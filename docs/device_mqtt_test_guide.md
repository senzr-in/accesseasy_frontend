# Access Control Board MQTT Protocol V1.0.6 Testing & Integration Guide

This document defines the complete testing specifications, MQTT topic mappings, and JSON payload structures for integrating Senzr-compatible Access Control Boards (CC104 / EC_B10) with the `device-mqtt` Knative service and the AccessEasy platform.

---

## 1. General Message Envelope Structure

All communications through the MQTT broker rely on a structured JSON envelope wrapper.

### Downlink Request (Platform → Device)
*   **Fields:**
    *   `uuid` (string, required): The device unique identifier (MAC address or Serial Number, minimum 8 characters).
    *   `serialNo` (string, required): A unique transaction identifier generated by the platform to trace command-reply loops (maximum 32 characters).
    *   `time` (integer, required): Unix timestamp of the request generation.
    *   `data` (object/array, required): The command-specific parameters.
    *   `sign` (string): Cryptographic signature for secure validation (optional/omitted in this staging setup).

```json
{
  "serialNo": "req_9f3b26c718a3d4ef",
  "uuid": "DEVICE_UUID_12345678",
  "time": 1782378800,
  "sign": "",
  "data": {}
}
```

### Uplink Event & Reply (Device → Platform)
*   **Fields:**
    *   `uuid` (string, required): The device unique identifier.
    *   `serialNo` (string, required): Must match the request `serialNo` if it is a command reply; otherwise, a unique value for autonomous events.
    *   `time` (integer, required): Unix timestamp.
    *   `code` (string, required in reply): Result code indicating success or error type.
        *   `000000`: Success.
        *   `100000`: General Unknown Error.
        *   `100001`: Device Disabled.
        *   `100002`: Device Busy (upgrading, sync, etc.).
        *   `100003`: Signature Verification Failed.
        *   `100004`: Request Timeout.
        *   `100005`: Device Offline.
        *   `200000` - `299999`: Parameter / Validation Error.
        *   `300000` - `399999`: Configuration / Field Permission Error.
    *   `message` (string, required in reply): Human-readable error description or success label.
    *   `data` (object/array, required): Return values (if any).

```json
{
  "serialNo": "req_9f3b26c718a3d4ef",
  "uuid": "DEVICE_UUID_12345678",
  "time": 1782378805,
  "code": "000000",
  "message": "Success",
  "sign": "",
  "data": {}
}
```

## 2. Device Uplink Events (Device → Platform)

Devices publish these events to global shared topics. The Knative bridge parses the payload's `uuid` to identify the device and maps the event to Directus.

### 2.1. Handshake / Boot Up (`connect`)
*   **Publish Topic:** `access_device/v1/event/connect`
*   **Expected Reply Topic (Device must subscribe):** `access_device/v1/event/{uuid}/connect_reply`
*   **Device Payload:**
    ```json
    {
      "uuid": "DEVICE_UUID_12345678",
      "serialNo": "boot_serial_001",
      "time": 1782378800,
      "data": {
        "IP": "192.168.1.105",
        "name": "Entrance Controller",
        "model": "CC104",
        "appVersion": "1.0.6",
        "sysVersion": "1.0.0"
      }
    }
    ```
*   **Platform Action:** 
    1. Updates the controller state to `online` in the `controllers` collection, or registers/updates it in the `mqtt_devices` staging collection.
    2. Publishes the standard `connect_reply` to `access_device/v1/event/{uuid}/connect_reply`.
    3. **Automated Configuration Push & Redirect:** Immediately after the handshake reply, the Knative service issues a `setConfig` command to `access_device/v1/cmd/{uuid}/setConfig` pushing the external/production MQTT configuration details (`MQTT_BROKER_EXTERNAL` env var, e.g. `mqtt.fieldseasy.com:1883`) so that the new device automatically configures its broker IP, port, credentials, and prefix. The device saves these settings to flash, replies, and reconnects to the production broker.


### 2.2. Disconnect notification (`disconnect`)
*   **Trigger:** Sent via Last Will & Testament (LWT) or EMQX Webhook on broker connection loss.
*   **Platform Action:** Flags device state as `offline` in Directus.

### 2.3. Event / Access Log Reporting (`access_record`)
Used to upload stored or real-time swipe history.
*   **Publish Topic:** `access_device/v1/event/access_record`
*   **Expected Reply Topic (Device must subscribe):** `access_device/v1/event/{uuid}/access_record_reply`
*   **Device Payload:**
    ```json
    {
      "uuid": "DEVICE_UUID_12345678",
      "serialNo": "event_serial_101",
      "time": 1782378820,
      "data": [
        {
          "type": 200,
          "code": "CARD_HEX_ABCDEF",
          "index": "01",
          "result": 1,
          "time": 1782378820
        }
      ]
    }
    ```
    *   *Credential Type Map (`type`):*
        *   `100` - `103`: QR Codes
        *   `200`: Standard RFID Card
        *   `201`: CPU Encryption Card
        *   `202`: Sector Encryption Card
        *   `300`: Face Verification
        *   `400`: Password Entry
        *   `500`: Fingerprint Scan
        *   `600`: Bluetooth Access
        *   `700`: License Plate
        *   `800`: Door Button
    *   *Access Result (`result`):* `1` = Granted (authorized), `0` = Denied (unauthorized).
    *   *Gate Index (`index`):* Hex bitmask of the door relay triggered (e.g. `"01"` = Door 1).

### 2.4. Real-Time Online Verification (`access_online`)
Sent when a device reads a credential but defers the validation decision to the cloud database.
*   **Publish Topic:** `access_device/v1/event/access_online`
*   **Expected Reply Topic (Device must subscribe):** `access_device/v1/event/{uuid}/access_online_reply`
*   **Device Payload:**
    ```json
    {
      "uuid": "DEVICE_UUID_12345678",
      "serialNo": "verify_serial_202",
      "time": 1782378900,
      "data": {
        "type": 200,
        "code": "CARD_HEX_ABCDEF",
        "index": "01"
      }
    }
    ```
*   **Knative Response (ALLOW):**
    ```json
    {
      "serialNo": "verify_serial_202",
      "uuid": "DEVICE_UUID_12345678",
      "code": "000000",
      "message": "Access granted",
      "time": 1782378901,
      "data": {}
    }
    ```
*   **Knative Response (DENY):**
    ```json
    {
      "serialNo": "verify_serial_202",
      "uuid": "DEVICE_UUID_12345678",
      "code": "100001",
      "message": "Card not found",
      "time": 1782378901,
      "data": {}
    }
    ```

### 2.5. Equipment Alarm Events (`alarm`)
Reports structural alarms, tamper, fire, or hardware status changes.
*   **Publish Topic:** `access_device/v1/event/alarm`
*   **Expected Reply Topic (Device must subscribe):** `access_device/v1/event/{uuid}/alarm_reply`
*   **Device Payload:**
    ```json
    {
      "uuid": "DEVICE_UUID_12345678",
      "serialNo": "alarm_serial_303",
      "time": 1782379000,
      "data": {
        "type": 0,
        "value": 1,
        "index": "01"
      }
    }
    ```
    *   *Alarm Type Map (`type`):*
        *   `0`: Door Sensor Status (`value`: `0` = closed, `1` = open)
        *   `1`: Fire Alarm Status (`value`: `0` = normal, `1` = active)
        *   `2`: Unauthorized Door Opening
        *   `3`: Door Opening Timeout
        *   `4`: Door Closing Timeout
        *   `5`: Firmware Upgrade Report (`value`: `0` = failed, `1` = success)
        *   `6`: Anti-Tamper Alarm (`value`: `0` = normal, `1` = tamper alarm triggered)
        *   `100`: Configuration Upload Notification
        *   `202`: M1 Config Card Read

## 3. Platform Downlink Commands (Platform → Device)

Commands are sent as HTTP POST requests to the Knative service router, which then translates and publishes them onto individual device topics.

### 3.1. Get/Query Configuration (`getConfig`)
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/getConfig`
*   **Uplink Reply Topic:** `access_device/v1/cmd/getConfig_reply`
*   **Knative Request Payload:**
    ```json
    {
      "serialNo": "cfg_req_001",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379100,
      "data": "netInfo" 
    }
    ```
    *(Note: Data field can be an empty string `""` to query all sections, or a specific string: `"sysInfo"`, `"netInfo"`, `"mqttInfo"`, `"doorInfo"`, or `"childInfo"`)*
*   **Device Acknowledgment Payload:**
    ```json
    {
      "serialNo": "cfg_req_001",
      "uuid": "DEVICE_UUID_12345678",
      "code": "000000",
      "message": "Success",
      "time": 1782379102,
      "data": {
        "netInfo": {
          "ip": "192.168.1.105",
          "subnet": "255.255.255.0",
          "gateway": "192.168.1.1",
          "dns": "8.8.8.8"
        }
      }
    }
    ```

### 3.2. Edit/Modify Configuration (`setConfig`)
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/setConfig`
*   **Uplink Reply Topic:** `access_device/v1/cmd/setConfig_reply`
*   **Knative Request Payload:**
    ```json
    {
      "serialNo": "cfg_req_002",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379150,
      "data": {
        "netInfo": {
          "ip": "192.168.1.200"
        },
        "mqttInfo": {
          "broker": "emqx.iot-services.svc.cluster.local"
        }
      }
    }
    ```
*   **Device Acknowledgment Payload:**
    ```json
    {
      "serialNo": "cfg_req_002",
      "uuid": "DEVICE_UUID_12345678",
      "code": "000000",
      "message": "Success",
      "time": 1782379153,
      "data": {}
    }
    ```

### 3.3. Add / Edit Permissions (`insertPermission`)
Permissions are whitelisted keys/credentials. Under the protocol, editing is achieved by executing `insertPermission` with an existing `id`. The hardware updates the record matching the ID.
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/insertPermission`
*   **Uplink Reply Topic:** `access_device/v1/cmd/insertPermission_reply`
*   **Knative Request Payload (Includes RFID Card & Fingerprint Example):**
    ```json
    {
      "serialNo": "perm_req_001",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379200,
      "data": [
        {
          "id": "perm_rfid_card1",
          "type": 200,
          "code": "CARD_HEX_998877",
          "index": "01",
          "time": { "type": 0 }
        },
        {
          "id": "perm_fingerprint_user2",
          "type": 500,
          "code": "FINGERPRINT_HEX_OR_BASE64_TEMPLATE_DATA",
          "index": "01",
          "time": { "type": 0 }
        }
      ]
    }
    ```
    *(Note: `time: { "type": 0 }` indicates permanent access. Use `{ "type": 1, "range": { "beginTime": 1782379200, "endTime": 1785000000 } }` for date-based scheduling).*
*   **Device Acknowledgment Payload:**
    ```json
    {
      "serialNo": "perm_req_001",
      "uuid": "DEVICE_UUID_12345678",
      "code": "000000",
      "message": "Success",
      "time": 1782379204,
      "data": {}
    }
    ```

### 3.4. Delete Specific Permissions (`delPermission`)
Deletes whitelisted records matching specific IDs.
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/delPermission`
*   **Uplink Reply Topic:** `access_device/v1/cmd/delPermission_reply`
*   **Knative Request Payload:**
    ```json
    {
      "serialNo": "perm_req_002",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379300,
      "data": [
        "perm_rfid_card1",
        "perm_fingerprint_user2"
      ]
    }
    ```
*   **Device Acknowledgment Payload:**
    ```json
    {
      "serialNo": "perm_req_002",
      "uuid": "DEVICE_UUID_12345678",
      "code": "000000",
      "message": "Success",
      "time": 1782379303,
      "data": {}
    }
    ```

### 3.5. Clear All Permissions Whitelist (`clearPermission`)
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/clearPermission`
*   **Uplink Reply Topic:** `access_device/v1/cmd/clearPermission_reply`
*   **Knative Request Payload:**
    ```json
    {
      "serialNo": "perm_req_003",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379350,
      "data": {}
    }
    ```
*   **Device Acknowledgment Payload:**
    ```json
    {
      "serialNo": "perm_req_003",
      "uuid": "DEVICE_UUID_12345678",
      "code": "000000",
      "message": "Success",
      "time": 1782379353,
      "data": {}
    }
    ```

### 3.6. Query Active Permissions stored on Device (`getPermission`)
Queries active credentials whitelisted on the hardware.
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/getPermission`
*   **Uplink Reply Topic:** `access_device/v1/cmd/getPermission_reply`
*   **Knative Request Payload:**
    ```json
    {
      "serialNo": "perm_req_004",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379400,
      "data": {
        "page": 0,
        "size": 50
      }
    }
    ```

## 5. Hardware Diagnostics & Control Actions (`remoteControl`)

Used to force state configurations, prompts, and reboots.
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/remoteControl`
*   **Uplink Reply Topic:** `access_device/v1/cmd/remoteControl_reply`

### 5.1. Restart Device (`command: 0`)
*   **Payload:**
    ```json
    {
      "serialNo": "ctrl_req_001",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379700,
      "data": {
        "command": 0
      }
    }
    ```

### 5.2. Open Door Relays (`command: 1`)
*   **Payload:**
    ```json
    {
      "serialNo": "ctrl_req_002",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379720,
      "data": {
        "command": 1,
        "index": "01"
      }
    }
    ```
    *(Note: `index: "01"` triggers Door 1 relay, `"02"` triggers Door 2, etc.)*

### 5.3. Activate Device (`command: 2`)
*   **Payload:** `{ "serialNo": "...", "uuid": "...", "data": { "command": 2 }, "time": ... }`

### 5.4. Disable Device (`command: 3`)
Blocks the device from responding to local scans.
*   **Payload:** `{ "serialNo": "...", "uuid": "...", "data": { "command": 3 }, "time": ... }`

### 5.5. Reset to Factory Configuration (`command: 4`)
*   **Payload:** `{ "serialNo": "...", "uuid": "...", "data": { "command": 4 }, "time": ... }`

### 5.6. Show Screen Prompt & Voice Wav (`command: 5`)
Useful to display customized messages and play voice prompts on swipe.
*   **Payload:**
    ```json
    {
      "serialNo": "ctrl_req_005",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379800,
      "data": {
        "command": 5,
        "extra": {
          "msg": "Welcome John Doe",
          "msgTimeout": 8,
          "wavFileName": "welcome.wav"
        }
      }
    }
    ```

### 5.7. Unified State Control (`command: 6`)
Sets explicit gate relay states (such as forcing a locked state).
*   **Payload (Lock Door 1):**
    ```json
    {
      "serialNo": "ctrl_req_006",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782379850,
      "data": {
        "command": 6,
        "index": "01",
        "extra": {
          "action": 0
        }
      }
    }
    ```
    *(Note: `action: 0` = Lock / Normal State, `action: 1` = Open / Unlocked State)*

## 7. Firmware Upgrades (OTA)

Initiates downloading and installing new firmware binary files.
*   **Downlink Topic:** `access_device/v1/cmd/{uuid}/upgradeFirmware`
*   **Uplink Reply Topic:** `access_device/v1/cmd/upgradeFirmware_reply`
*   **Payload:**
    ```json
    {
      "serialNo": "fw_req_001",
      "uuid": "DEVICE_UUID_12345678",
      "time": 1782380000,
      "data": {
        "type": 0,
        "url": "http://firmware-repo.local/firmware/cc104_v1.0.7.bin",
        "md5": "d41d8cd98f00b204e9800998ecf8427e"
      }
    }
    ```
    *   *Upgrade Type (`type`):* `0` = Local Device, `1` = Sub-device, `2` = Elevator Board.
    *   *Sub-device specifications:* If `type: 1`, payload requires `extra` field detailing the sub-device parameters:
        ```json
        "extra": {
          "deviceIndex": "01",
          "deviceModel": "CC104-SubBoard",
          "deviceVersion": "1.0.1"
        }
        ```
*   **Device Upgrade Report Event:**
    Upon completing the download and executing flash, the device reports the result status back via the alarm event `type: 5` (`value: 1` = Success, `0` = Failure) and boots back online.

## 8. AccessEasy UI Testing Workflows

Follow these step-by-step visual instructions to test, approve, control, and sync credentials using the AccessEasy frontend application.

### 8.1. Registering & Onboarding a Discovered Device
When your physical board or simulator connects to the MQTT broker and fires a `connect` handshake event, it enters the staging area. To approve and activate it:
1.  Navigate to **Settings** in the sidebar (Admin view) and click **Devices** (Path: `/dashboard/settings/devices`).
2.  Click the **Add Hardware Device** button on the top right.
3.  Click the **Scan Network** button (highlighted with a Wifi icon) inside the Serial Number input.
    *   *This fetches a list of discovered controllers currently registered in the `mqtt_devices` Directus staging collection.*
4.  Select your device (matching your `uuid` / MAC address) from the list. The system will auto-fill the Serial Number, IP, and MAC address.
5.  Enter a custom device name (e.g. "Main Lobby Controller").
6.  Select the **Device Type** matching the board's relay configuration (Single-Door, 2-Door, 3-Door, or 4-Door).
7.  If your device communicates via direct IP (TCP/UDP), toggle **Direct IP Connection** on. If it communicates directly via MQTT, leave this toggled off.
8.  Click **Register Hardware**.
    *   *The device will move to the active `controllers` collection, and AccessEasy will immediately send a `clearPermission` downlink command via MQTT to format the device database.*

### 8.2. Binding a Door to a Device
1.  Navigate to **Doors** in the sidebar (Path: `/dashboard/access-control/doors`).
2.  Click **Add Door** (or click **Edit** on an existing door in the table).
3.  Enter a name (e.g., "Front Main Gate") and a physical location.
4.  Specify the **Door Number** (e.g., `1` to match index `"01"` in the MQTT payloads).
5.  In the **Device** dropdown list, select your registered controller's Serial Number/UUID.
6.  Click **Save**.

### 8.3. Testing Remote Door Control (Open / Lock)
1.  Navigate to the **Doors** page (Path: `/dashboard/access-control/doors`).
2.  In the doors list, hover over your configured door's row to reveal action buttons.
3.  Click the **Open** button:
    *   *AccessEasy sends an HTTP request to the Knative service `/device-router` which publishes a `remoteControl` command (`command: 1`) to the device's MQTT topic.*
    *   *Verify that your device receives the payload on `access_device/v1/cmd/{uuid}/remoteControl` and triggers the relay.*
4.  Click the **Lock** button:
    *   *AccessEasy publishes a unified lock command (`command: 6`, `action: 0`).*
    *   *Verify that your device locks the door and replies to `remoteControl_reply` with code `"000000"`.*

### 8.4. Registering and Syncing RFID Cards
1.  Navigate to **Employees** in the sidebar (Path: `/dashboard/easy-access/employees`).
2.  Select an employee from the table to open their profile.
3.  Go to the **Access Management** tab and click **Edit**.
4.  Select **Add Card**, enter the card's HEX code (e.g., `CARD_HEX_ABC123`), select the active doors the card has permission for, and click **Save**.
    *   *AccessEasy automatically triggers an `insertPermission` command (`type: 200`) to sync the card down to the controller.*
    *   *Verify that the controller receives the `insertPermission` topic and inserts the card ID into its memory.*

### 8.5. Registering and Syncing Fingerprints
1.  Navigate to the **Fingerprint Management** dashboard directly (Path: `/dashboard/easy-access/biometrics/fingerprint`).
2.  Click the **Add Finger** button on the top right.
3.  Select the employee you wish to enroll, choose the finger index (e.g., Right Index), capture the template data, and click **Save**.
    *   *AccessEasy pushes the fingerprint template to the controller via an `insertPermission` command (`type: 500`).*
4.  **To delete:** Locate the employee's finger record in the dashboard table and click the **Trash** icon. Confirm deletion.
    *   *AccessEasy will send a `delPermission` command to delete the fingerprint ID from the controller's memory.*

### 8.6. Registering Face Biometrics
1.  Navigate to the **Face Embedding** dashboard directly (Path: `/dashboard/easy-access/biometrics/face`).
2.  Click **Add Face**.
3.  Select the employee, upload their profile picture (or capture via connected webcam), and click **Save**.
    *   *AccessEasy transmits the Base64 image payload to the Knative bridge, which publishes an `insertFace` command to the device's face database.*
